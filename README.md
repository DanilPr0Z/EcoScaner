# BinGo

Сканируешь фото мусора — узнаёшь, в какой бак его выбросить, как подготовить
и во что он переработается.

**Живой сайт: [72.56.38.224](http://72.56.38.224)** — работает, распознаёт,
ничего ставить не нужно.

> Съёмка с камеры прямо на странице там недоступна: браузеры дают доступ
> к камере только по HTTPS, а сайт открыт по обычному HTTP. Загрузка файла
> и вставка из буфера работают. Лечится доменом с сертификатом.

* **Бэкенд** — FastAPI: справочник отходов, распознавание фото, профиль с очками
  и достижениями. Каталог `app/`.
* **Фронтенд** — React + TypeScript + Vite. Каталог `frontend/`.

Распознавание — YOLOv8, спрятанный за протоколом `Classifier`. По умолчанию
работает заглушка, чтобы приложение поднималось без тяжёлых зависимостей;
включение реальной модели — две команды, см. [«Подключение ML»](#подключение-ml).

## Запуск

```bash
./start.sh
```

Скрипт поднимает оба сервера, а недостающие зависимости (venv, pip, npm) ставит
сам при первом запуске. Ctrl+C останавливает всё разом.

* приложение — http://localhost:5173
* документация API — http://localhost:8000/docs

Можно запустить что-то одно: `./start.sh back` или `./start.sh front`.

<details>

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload                       # http://localhost:8000
```

```bash
cd frontend && npm install && npm run dev           # http://localhost:5173
```

</details>

При старте бэкенд создаёт недостающие таблицы и заполняет справочник,
поэтому отдельный шаг с миграциями не нужен. Vite проксирует `/api` на FastAPI,
так что CORS в разработке не участвует и ничего настраивать не надо.

Если ведёте схему через Alembic, поставьте в `.env` `AUTO_CREATE_TABLES=false`
и накатывайте миграции сами:

```bash
alembic upgrade head
```

Настройки — в `.env` (см. `.env.example`), значения по умолчанию — в `app/core/config.py`.

## Модель и данные

Материал определяет классификатор **YOLOv8s-cls**, обученный на 16 070 снимках
в 10 классах. Классы модели сворачиваются в 7 категорий справочника — те, что
видит пользователь:

| Категория | Классы модели |
|---|---|
| пластик | Plastic |
| стекло | Glass |
| бумага | Cardboard, Paper |
| металл | Metal |
| органика | Food Organics, Vegetation |
| особые отходы | Battery |
| прочее | Textile Trash, Miscellaneous Trash |

Разделение не случайное: картон и бумага — разные вещи для модели и одна
для пользователя, путаница между ними ему не вредит, бак у них общий.

### Откуда данные

| Источник | Снимков | Чем полезен |
|---|---|---|
| [RealWaste](https://www.mdpi.com/2078-2489/14/12/633) | 4 752 | Реальный мусоросортировочный полигон: предметы на конвейере и земле |
| [Garbage-12](https://huggingface.co/datasets/UdaraChamidu/Garbage-Classification-with-12-classes) | 9 818 | Студийная съёмка на белом фоне; единственный источник батареек |
| [Organic O/R](https://huggingface.co/datasets/bryandts/waste_organic_anorganic_classification) | 1 500 | Органика, которой в RealWaste почти нет |

Источники намеренно разные по условиям съёмки. Модель, обученная на одном
домене, цепляется за фон и оттенок: на снимках только с полигона матовая белая
бутылка уезжала в «бумагу» просто потому, что светлая. Одна категория в двух
разных доменах такой возможности не оставляет.

Каждый источник приводится к нашим классам, крупные классы подрезаются
(одежды и обуви в Garbage-12 семь тысяч — без потолка «прочее» перевесило бы
всё остальное), копии одного кадра целиком уезжают в одну сторону разбиения.

### Точность

| Выборка | Точность по категориям | Что означает |
|---|---|---|
| train | 100.0% | Модель видела эти снимки |
| val | 97.2% | Те же датасеты, отложенные снимки |
| **test** | **91.0%** | **Четвёртый датасет, которого в обучении не было** |

Смотреть нужно на третью строку. Валидация нарезана из тех же датасетов,
что и обучение: она меряет, насколько модель их выучила, а не насколько
работает на обычных фотографиях. Независимый тест — 750 снимков из источника,
на котором не учились, с проверкой, что ни один кадр не совпадает
с обучающими.

По категориям на независимом тесте: бумага 96%, пластик 90%, стекло 90%,
металл 82%.

Разрыв val→test — 6.2 п.п. Больше десяти означало бы, что валидация врёт
и её нужно пересобирать.

### Чего модель не умеет

* **Один предмет на кадр.** Классификатор выдаёт одну метку. На фотографии
  с пакетом, кожурой и бумагой он назовёт то, что занимает больше площади —
  формально не ошибётся, но и не поможет.
* **Белые матовые цилиндры.** Алюминиевая банка, бумажный стакан и пластиковая
  бутылка в такой форме похожи; это главный источник ошибок между металлом,
  бумагой и пластиком.
* **Посторонние предметы в кадре.** Часть датасетов снята на конвейере или
  на белом фоне. Это лечилось добавлением уличных снимков TACO и бытовых
  из Open Images, но перекос в сторону студийной съёмки остался.
* **Гранёное стекло на солнце.** Продольные блики на рифлёном стакане дают
  ту же картинку, что полированный алюминий. Живой случай: определился
  металлом с уверенностью 0.89. Смесь моделей снизила уверенность до 0.62,
  но ответ пока неверный.

### Сколько она даёт

Меряется на независимом тесте: 1200 снимков из четырёх чужих датасетов,
которых не было в обучении, — каждый проверен по перцептивному отпечатку.
Покрыты все семь категорий справочника.

| категория | боевая | смесь трёх |
|---|---|---|
| органика | 100.0% | 100.0% |
| бумага | 96.7% | 96.3% |
| прочее | 97.3% | 94.7% |
| пластик | 91.3% | 93.3% |
| особые отходы | 88.0% | 90.7% |
| стекло | 88.7% | 90.0% |
| металл | 81.3% | **90.0%** |
| **всего** | 92.5% | **93.9%** |

Работают три модели сразу, ответы усредняются равными долями: они сильны
в непересекающихся местах. Доли равные намеренно — подбор весов давал
на своей половине теста 94%, а на чужой 92%, то есть подбирался шум.
Равные доли выигрывают на обеих половинах. Цена — 41 мс на снимок вместо 10.

Худшая категория поднялась с 81.3% до 90.0%: для пользователя с банкой
в руках это важнее средней цифры.

### Как измеряется

```bash
python -m prediction.preflight          # проверка, что настройки доходят
python -m prediction.build_testset      # независимый тест
python -m prediction.extend_testset     # органика, текстиль, батарейки
python -m prediction.train_classifier   # обучение
```

`preflight` появился не зря: за один день трижды выяснилось, что параметр
принимается, печатается в справке и не делает ничего. Все находки —
в `docs/known-issues.md`.

Обучение пишет ход в `runs/realwaste/results.csv` и сводку в
`prediction/metrics.json`. Страница «Модель» в приложении показывает точность
и потери по эпохам, причём **по ходу обучения**, а не только в конце.

## Пользователь

Регистрации нет. Фронт один раз генерирует UUID (`crypto.randomUUID()`), хранит
его в `localStorage` и шлёт с каждым запросом в заголовке `X-Device-Id` — по нему
бэкенд ведёт профиль, историю и очки. Запись о пользователе заводится сама при
первом запросе.

## Эндпоинты

Базовый префикс — `/api/v1`. Поля ответов в **camelCase**, чтобы TS-фронт
потреблял их без маппинга. Типы ответов — `frontend/src/api/types.ts`,
клиент — `frontend/src/api/client.ts`.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/health` | Статус и активная модель (`stub` / `ml`) |
| GET | `/categories` | Все 7 категорий с предметами |
| GET | `/categories/{id}` | Одна категория |
| GET | `/guide/search?q=&limit=` | Поиск по всему тексту справочника |
| POST | `/scan` | `multipart/form-data`, поле `file` — распознать фото |
| POST | `/scan/manual` | Ручной выбор категории |
| POST | `/scan/{id}/correct` | «Модель ошиблась» — перенести скан в верную категорию |
| GET | `/profile` | Очки, серия дней, распределение по бакам, бейджи |
| GET | `/profile/history?limit=` | История сканирований |
| DELETE | `/profile/history` | Очистить историю и очки |

### Поиск по справочнику

`GET /guide/search` ищет не только по названиям предметов, но и по примечаниям,
описаниям категорий, подсказкам, шагам подготовки и полям «разлагается» /
«станет». Отвечает двумя списками: `items` — подходящие предметы, `categories` —
категории, чей собственный текст отвечает запросу (например, «метан» встречается
только в подсказке про органику).

Что умеет:

* регистр и «ё»/«е» — «жёлтый» и «желтый» ищут одинаково;
* словоформы — «бутылки», «бутылке», «бутылку» находят «Бутылка из-под воды»;
* незаконченное слово — «бутыл» уже находит;
* опечатку в один символ — «бутулка» находит;
* несколько слов объединяются по И: «консервная банка» — да, «консервная гитара» — нет.

Выдача отсортирована по релевантности: совпадение в названии предмета весит
больше, чем в примечании, а оно — больше, чем в описании категории. Поле
`matchedIn` говорит, за какие именно поля строка попала в выдачу — удобно
подсветить причину в интерфейсе. `total` — сколько нашлось всего, до `limit`.

Реализация — `app/services/text_search.py`, без внешних зависимостей: SQL `LIKE`
здесь не годится, потому что у SQLite регистронезависимое сравнение работает
только для латиницы, и «бутылка» не находила бы «Бутылка из-под воды».

`POST /scan` возвращает предсказание **вместе** с контентом категории (подсказка,
шаги подготовки, срок разложения, что делать нельзя) — одним запросом заполняется
вся правая колонка экрана сканера.

Коды ошибок, которые фронту стоит обработать на экране сканера: `415` — не
изображение, `413` — файл больше лимита, `400` — пустой файл или нет заголовка
`X-Device-Id`, `422` — предмет не распознан (показываем блок ошибки и кнопки
ручного выбора, затем `POST /scan/manual`). Текст в поле `detail` уже на русском
и годится для показа пользователю.

## Снимки пользователей и дообучение

Снимки сохраняются — без них исправления категорий остаются пометками в базе,
и учиться не на чем. Имя файла это SHA-256 содержимого, поэтому одинаковые
кадры не плодят копий.

У этого есть немедленный эффект: если кадр уже исправляли, ответ берётся
из исправления, а модель даже не запускается. Один и тот же файл не нужно
править дважды — и это работает для всех, не только для того, кто исправил.

```bash
python -m prediction.export_feedback    # исправления → обучающая выборка
python -m prediction.train_classifier   # переобучение
```

Порог `--min-per-class` не даёт выгрузить класс с горсткой примеров: десяток
снимков одного предмета модель не научит, зато уверенно сместит её в его сторону.

Неисправленные снимки удаляются через `UPLOADS_KEEP_DAYS`, исправленные
остаются — они и есть та выборка, ради которой всё затевалось.

**Это персональные данные.** В кадр попадают интерьер, документы, люди.
Хранение выключается одной настройкой `STORE_UPLOADS=false`; перед публичным
запуском нужна строчка в условиях использования.

Ещё одно ограничение, о котором стоит знать: сейчас любое исправление
принимается как истина и действует на всех. На демонстрации это правильно,
в проде один недобросовестный человек сможет назначить бутылке категорию
«органика» для всех — лечится порогом в два-три независимых подтверждения.

## Подключение ML

Единственный контракт модели — `app/services/recognition/base.py`:

```python
class Classifier(Protocol):
    name: str
    async def predict(self, image: bytes, content_type: str) -> Prediction | None: ...
```

`Prediction` — это `category_id`, `object_name`, `confidence`, рамки и строки для
блока «Что увидела нейросеть». `None` означает «не распознано» — роутер превратит
это в `422`, и пользователь выберет категорию вручную.

Материал определяет классификатор, обученный на датасете
[RealWaste](https://www.mdpi.com/2078-2489/14/12/633) — 4752 снимка отходов
с реального мусороперерабатывающего полигона, 9 классов.

```bash
pip install -r requirements-ml.txt          # ultralytics + pillow, тянет torch
python -m prediction.train_classifier       # обучение, веса лягут в prediction/
echo "CLASSIFIER=ml" >> .env
```

Проверить, что модель активна: `GET /api/v1/health` вернёт `"classifier": "ml"`.

### Обучение

`prediction/train_classifier.py` сам делит RealWaste на train/val симлинками
(датасет весит 666 МБ, копировать его незачем), обучает YOLOv8-cls и кладёт
лучшие веса в `prediction/waste_classifier.pt`. Разбиение детерминировано
seed — повторный запуск даёт тот же split, иначе метрики между запусками
несравнимы.

```bash
python -m prediction.train_classifier --epochs 40        # дольше и точнее
python -m prediction.train_classifier --model yolov8m-cls.pt
```

Датасет ожидается в `realwaste-main/RealWaste` (папка на класс). Ни датасет,
ни веса, ни артефакты обучения в git не попадают.

### Почему классификация, а не детекция

RealWaste — набор снимков по папкам-классам, рамок в нём нет, обучить на нём
детектор нельзя. Приложению детекция и не нужна: пользователь снимает один
предмет крупно, вопрос стоит «из чего это», а не «где это на кадре».
Классификатор при этом знает картон, текстиль и смешанный мусор — то, чего
в COCO попросту нет.

Детектор COCO остался, но только ради рамки на фото и уточнения названия
(«пластиковая бутылка» вместо «пластик»). На выбор категории он не влияет
и отключается: `DETECTOR_WEIGHTS=`.

### Как устроен адаптер

`app/services/recognition/ml.py`:

* фото приходит байтами и остаётся в памяти — на диск ничего не пишется;
* обе модели загружаются один раз при старте (`warmup`), а не на каждый запрос;
* инференс уходит в отдельный поток, иначе на время счёта встаёт весь сервер;
* рамки пересчитываются в проценты — фронт рисует их поверх своего превью;
* русские названия категорий переводятся в id справочника.

Таблицы классов не дублируются: `REALWASTE_CLASSES_RU` и `COCO_CLASSES_RU`
импортируются из модулей моделей. Если там появится категория, которой нет
в справочнике, приложение упадёт на старте с указанием, что добавить.

### Как работает заглушка

`StubClassifier` детерминирован хэшем картинки: одно фото всегда даёт один и тот же
ответ. Примерно на 5% изображений отвечает «не распознано» — чтобы фронтовый экран
ошибки тоже можно было проверить.

## Структура

```
app/
├── main.py                 # сборка приложения, CORS, старт (создание таблиц + сид)
├── core/                   # настройки и зависимости (сессия БД, X-Device-Id)
├── data/seed_data.py       # справочник отходов и словари меток
├── db/                     # модели, сессия, сид
├── schemas/                # схемы ответов (camelCase наружу)
├── services/
│   ├── guide.py            # выборка и поиск по справочнику
│   ├── gamification.py     # очки, серия дней, бейджи
│   └── recognition/        # ГРАНИЦА ML: протокол, заглушка, модель, выбор реализации
└── api/v1/                 # роутеры
prediction/
├── train_classifier.py     # обучение классификатора на RealWaste
├── model_training.py       # таблица классов COCO (от ML-разработчика)
└── waste_classifier.pt     # обученные веса (в git не хранятся)
```

Контент справочника (7 категорий, ~50 предметов) лежит в `app/data/seed_data.py`
и переносится в БД при каждом старте. Правка текста + перезапуск — и фронт видит
изменения без пересборки.
